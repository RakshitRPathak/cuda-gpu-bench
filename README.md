# cuda-gpu-bench

[![emulator-tests](https://github.com/RakshitRPathak/cuda-gpu-bench/actions/workflows/ci.yml/badge.svg)](https://github.com/RakshitRPathak/cuda-gpu-bench/actions/workflows/ci.yml)

Hand-written CUDA kernels, benchmarked and analysed the way a GPU performance engineer
would: *where is the time going, and is this kernel limited by compute, memory, or
synchronization?*

| Experiment | Kernels | Question it answers | Metric |
|---|---|---|---|
| Vector add | `vec_add` | What does a purely memory-bound kernel look like? | GB/s vs peak DRAM bandwidth and `cudaMemcpy` |
| Matrix multiply | `matmul_naive`, `matmul_tiled`, cuBLAS (optional) | How much does shared-memory tiling help? How far is a hand-written kernel from a tuned library? | GFLOP/s |
| Sum reduction | `reduce_atomic`, `reduce_shared`, `reduce_warp` | What does synchronization cost? Atomics vs shared-memory tree vs warp shuffles | GB/s |
| PyTorch | small transformer under `torch.profiler` | Which ops dominate, and why? FP32 vs TF32 vs FP16 | ms, TFLOP/s, Chrome trace |

## Status: what has and has not been verified

The kernels were first written and checked on a machine without a GPU, then built with `nvcc`
and measured on a Tesla T4 (Google Colab, October 2026) and on a GeForce RTX 5050 Laptop GPU
(November 2026).

| Check | Result |
|---|---|
| Kernel logic run on the CPU through an emulator (`make emulate`), 33 checks against reference code | passes |
| Same under AddressSanitizer + UBSan, and ThreadSanitizer | pass, no reports |
| Do the checks have teeth? Deliberately broken kernels (wrong index, off-by-one in the tree, missing `__syncthreads`, dropped bounds check, missing atomic) | all caught by the emulator or a sanitizer |
| `bench.cu` parses and type-checks as CUDA (clang, host and device passes, with and without cuBLAS) | passes, against stand-in CUDA headers, not NVIDIA's real ones |
| Kernels compile to PTX (`ptx/kernels_sm80.clang.ptx`, generated by clang) | all 6 kernels |
| `bench.cu` built with `nvcc` (`sm_75`, with cuBLAS) and run on a Tesla T4 | **done**: every kernel passes the CPU-reference check, results below |
| `bench.cu` built with `nvcc` for `sm_120` and run on a GeForce RTX 5050 Laptop GPU (WSL2) | **done**: results below, raw CSVs in `results/` |
| `python/profile_pytorch.py` run with real PyTorch | **not done**; only its control flow was smoke-tested against a fake `torch` |

## Run it

```bash
# 1. No GPU needed: unit-test the kernel logic on the CPU (g++ >= 11)
make emulate            # also: make emulate-asan   make emulate-tsan

# 2. On a machine with an NVIDIA GPU and the CUDA toolkit
make run                # builds ./bench, verifies every kernel, benchmarks, writes results/results.csv
make cublas && ./bench_cublas     # adds a cuBLAS baseline for matmul
python3 tools/summarize_results.py results/results.csv

# 3. PyTorch profiling (any machine; GPU recommended)
pip install torch
python python/profile_pytorch.py --train --peak-tflops <fp32 TFLOP/s> --peak-gbps <GB/s>
#    then open results/pytorch_trace.json in https://ui.perfetto.dev
```

`./bench` first verifies every kernel against a CPU reference (including sizes that are not
multiples of the tile) and refuses to benchmark a kernel that is wrong.
If `-arch=native` is rejected (CUDA older than 11.6): `make ARCH=sm_75` (T4), `sm_80` (A100),
`sm_86` (RTX 30xx), `sm_89` (RTX 40xx).

Free GPUs for the first run: Google Colab (T4) or Kaggle notebooks.

## What the T4 numbers show

**Tiling helped less than the theory says: 1.5×, not 16×.** Tiling cuts global loads by
about 16× on paper, but the naive kernel's loads go through the read-only cache
(`ld.global.nc`, from `const __restrict__`), and neighbouring threads re-read the same rows
and columns from L1/L2. So the naive kernel was never paying full DRAM cost per load. The
tiled kernel is also limited by doing one output per thread with no register tiling: each
FMA still needs a shared-memory load. That is why it sits at about 15% of cuBLAS, and why
register tiling and `float4` loads are the next steps (see Design notes).

**Matmul throughput falls as N grows** for both hand-written kernels (naive 617 → 447,
tiled 959 → 683 GFLOP/s). The working set of a row of A and a column of B grows with N,
so less of it stays in cache. cuBLAS stays at 4.7–5.5 TFLOP/s, about 57–68% of the T4's
FP32 peak.

**`vec_add` beat `cudaMemcpy`** (257 vs 233 GB/s), so device-to-device memcpy is not a hard
bandwidth ceiling. Both count bytes the same way (read + write), but `vec_add` reads two
streams for every one it writes, and a read-heavy mix usually gets more out of DRAM than a
1:1 copy does. The
better yardstick is the 320 GB/s peak: `vec_add` reaches 80% of it.

**Reductions are memory-bound, and atomics cost about 38%.** The shared-memory tree and the
warp-shuffle version tie at about 234 GB/s (73% of peak): both stream the input once and do
a single atomic per block, so the different in-block synchronization (9 barriers vs 1
barrier + 10 shuffles) is hidden behind memory time. `reduce_atomic` also uses a
grid-stride loop, but then every thread does its own `atomicAdd` on the same address, 256×
as many atomics as the other two. Those serialize at the L2, and it reaches only 170 GB/s.

## What changes on Blackwell (RTX 5050 vs T4)

**cuBLAS is 1.25× faster at N = 1024 and 1.44× faster at N = 2048** (6.7–6.9 vs 4.7–5.5 TFLOP/s).
A later run on the same laptop, PTXForge's tuner on 17 November with the laptop plugged in and in its performance power
mode, measured cuBLAS SGEMM at 9.5 TFLOP/s for N = 2048, about 40% above the 6.7 here. The likeliest reason is that this
run was in a lower power state, but that has not been checked. Treat these as numbers for one power state, and compare
kernels within a run rather than across runs. Re-running `./bench_cublas` in performance mode would settle it.

**Tiling is worth less: 1.27–1.35× instead of 1.53–1.56×.** The naive kernel gained more from the new
GPU (+60% at N = 2048) than the tiled kernel did (+34%). A likely reason is cache: Blackwell has far more
L1 and L2 than the T4's 4 MB of L2, so more of the naive kernel's repeated row and column reads hit cache
and tiling has less DRAM traffic left to save. The tiled kernel still does one output per thread with a
shared-memory load for every FMA, so it sits at 14–22% of cuBLAS on both GPUs. Register tiling matters
even more here.

**Reductions fall well short of `vec_add` (46–53% of peak vs 71%), and the atomic penalty shrinks from
38% to 15%.** Both point to the same cause, which is a hypothesis until it is measured: too few memory
requests in flight. The grid is 8 blocks per SM, so 160 blocks here against 320 on the T4, but each
RTX 5050 SM has to feed 19 GB/s of DRAM bandwidth (384 / 20) against 8 GB/s per T4 SM (320 / 40). That is
2.4× more data per SM with the same number of threads, each loading one `float` per loop iteration, so
all three kernels wait on memory and the extra atomics cost less in comparison. The test is to sweep the
number of blocks per SM (8, 16, 32, 64): if bandwidth climbs toward `vec_add`'s 272 GB/s, the next step is
`float4` loads or unrolling the grid-stride loop, which add loads in flight without adding blocks.

## Reading the PTX

PTX is NVIDIA's virtual GPU assembly: the format `nvcc` emits and the driver compiles to
real machine code (SASS). `tools/ptx_summary.py` counts the instructions that matter. This
is the output for the kernels here, **compiled by clang** (`ptx/kernels_sm80.clang.ptx`);
`make ptx` produces nvcc's version, which will differ in details such as unrolling.

```
kernel                 ld.global ld.shared st.shared st.global       fma  bar.sync      shfl      atom
vec_add                        2         0         0         1         0         0         0         0
matmul_naive                   6         0         0         1         3         0         0         0
matmul_tiled                   2        32         2         1        16         2         0         0
reduce_atomic<...>             1         0         0         0         0         0         0         1
reduce_shared<...>             1        17         9         0         0         9         0         1
reduce_warp<...>               1         1         1         0         0         1        10         1
```

What it shows:

* `matmul_naive`: the loop body (unrolled by clang) pairs **two global loads with every
  FMA**, and the loads are `ld.global.nc`, the read-only cache path enabled by
  `const ... __restrict__`.
* `matmul_tiled`: the 16-iteration inner loop is fully unrolled, 16 FMAs fed by
  `ld.shared`, with exactly **2 `bar.sync`** per tile (load barrier, reuse barrier) and only
  2 global loads per tile.
* `reduce_shared` needs **9 barriers** (1 + log2(256) = 8 tree levels); `reduce_warp` needs
  **1 barrier + 10 `shfl.sync`** (5 per stage); `reduce_atomic` has none but one `atom` per
  thread. That is the synchronization trade-off, visible in the instructions.

To go deeper, dump machine code and profile a real kernel:

```bash
cuobjdump -sass bench | less                    # SASS, what actually runs
ncu --set full -k matmul_tiled -c 1 ./bench --skip-verify --sizes 1024   # Nsight Compute
nsys profile -o timeline ./bench --skip-verify  # Nsight Systems timeline
```

## Layout

```
src/kernels.cuh        all GPU kernels (no runtime calls, so the CPU emulator can include it)
src/common.cuh         CUDA_CHECK, GPU event timer, RAII device buffer
src/bench.cu           verification + benchmarks + CSV output
test/cuda_shim.hpp     CPU emulation of threads, blocks, shared memory, __syncthreads, atomics, shuffles
test/emulate_kernels.cpp   unit tests that run the real kernels through the shim
python/profile_pytorch.py  torch.profiler experiments
tools/ptx_summary.py   per-kernel PTX instruction counts
tools/summarize_results.py speedup summary of results.csv
ptx/                   PTX generated for sm_80
```

## Design notes and limits

* The emulator runs blocks one after another, so it checks intra-block logic (indexing,
  shared-memory tiling, barriers, shuffles) but not races *between* blocks.
* Atomic float adds are not associative, so reduction results vary slightly between runs;
  verification uses a relative tolerance.
* Timing uses CUDA events with warm-up runs and averages over `--iters` launches. Results
  depend on clocks and thermals; run a few times.
* `matmul_tiled` is a classic teaching kernel, not a competitive one. Natural next steps:
  register tiling (each thread computes a 4x4 patch), vectorized `float4` loads, padding
  shared memory to avoid bank conflicts, double buffering, and Tensor Cores via WMMA.
